# Story 1.12.5: OpenTelemetry Observability Pipeline

**Epic 1: Docker Service**
**Story Number:** 1.12.5 (interstitial — bridges 1.12 and 1.13)
**Status:** review

## Story

As a wiki operator running this service in a production-adjacent environment,
I want OpenTelemetry instrumentation (traces, metrics, structured logging) baked into the service,
So that I can ship telemetry data to Grafana Alloy (or any OTLP collector) for downstream visualization, alerting, and analytics without SSH-ing into the container.

**Context:** Story 1.12 added `QueryLogStore` with a non-fatal failure path, but there is no external-facing observability surface. The service currently has no OTel lifecycle, no trace/span emission for HTTP requests, no metrics exporters, and no OTLP endpoint for log aggregation. Grafana Alloy (or similar OTLP receivers) expects structured telemetry via the OTLP protocol — not a Prometheus scrape endpoint. This story installs the OTel SDK, auto-instrumentation, and OTLP exporters for traces, metrics, and logs into the service. Grafana Alloy will be the consumer, not a dependency of the service itself.

**Goal:** Emitter-only OTel. The service exports OTLP trace/metric/log data via gRPC or HTTP to a configured collector. Alloy is a deployment-era concern, not a code dependency.

## Acceptance Criteria

1. **Given** the service is running **When** it starts **Then** the OTel SDK initializes: traces, metrics, and logs are configured with an OTLP exporter (gRPC or HTTP, configurable via `OTEL_EXPORTER_OTLP_PROTOCOL` or `OTEL_EXPORTER_OTLP_ENDPOINT` env vars). The SDK uses a `BatchSpanProcessor` for traces — not a simple sync one — with reasonable defaults (5s delay, 512 max batch size) that keep memory bounded and network efficient.

2. **Given** FastAPI requests are served **When** auto-instrumentation is installed **Then** a trace/root-span is emitted per request using `opentelemetry-instrumentation-fastapi`. Each Grafana/Alloy trace shows HTTP method, route, latency, and status code. HTTP attributes follow OpenTelemetry semantic conventions (e.g., `http.request.method`, `http.response.status_code`).

3. **Given** `QueryLogStore` fails to initialize during lifespan startup **When** it fails **Then** an exception is recorded on the lifespan span via `span.record_exception()`, and a `wiki_query_log_init_failed` metric gauge is set to 1 so Grafana can alert on startup failures.

4. **Given** any exception occurs in `QueryLogStore.log()` and is caught **When** it is caught **Then** the existing `logger.error()` call is augmented with a counter increment: `query_log_write_failures_total` recorded via `opentelemetry.metrics.get_meter("llm_wiki").create_counter("query_log_write_failures_total")`. This counter surfaces in Grafana dashboards so query log write failure rate can be alerted on externally.

5. **Given** OTel SDK is configured for log correlation **When** a log line is emitted **Then** every log line emitted in production includes the OTel `trace_id` and `span_id` (injected via Python logging integration) so Grafana/Alloy LogQL or log filters can correlate logs with traces by `trace_id` or `span_id`.

6. **Given** OTel exporters fail to connect (e.g., Alloy is down, network unavailable, or endpoint misconfigured) **When** the SDK tries to export **Then** the SDK handles this gracefully via its internal worker thread (backpressure with drop on queue full, no crash, no request blocking).

**Pre-existing implementation note:** The lifespan already wraps `QueryLogStore(...)` in try/except and sets `app.state.query_log_error` on failure. The health handler already reads this and returns `query_log_ok`. Story 1.12.5 must not break this.

## Dev Notes

### Design Decision: OTel vs Prometheus

**Decision: OpenTelemetry (OTel) over Prometheus-native metrics/scrape endpoint.**

Rationale: The target is Grafana Alloy — an OTLP collector. Alloy natively supports OTLP receivers (metrics, logs, traces over gRPC and HTTP). A push model means the API doesn't expose a scrape endpoint that needs to be secured. Alloy handles:
- OTLP receiver (native, high-performance, scalable)
- Direct metric ingestion from OTel metrics
- Log ingestion from OTel logs (`/v1/logs` collector)
- PromQL queries / Grafana dashboards built from OTel `trace_id`/`span_id` extracted from log fields

The OTel Python SDK provides:
- `opentelemetry-api` — no-op interfaces, very lightweight
- `opentelemetry-sdk` — actual implementations
- `opentelemetry-instrumentation-fastapi` — automatic HTTP route/span/metric emission
- `opentelemetry-exporter-otlp-proto-grpc` + `otlp-proto-http` — push to Alloy
- `opentelemetry-semantic-conventions` — standard attribute names

Do NOT build manual instrumentation (Counters, Gauges, Histograms) — `opentelemetry-instrumentation-fastapi` handles HTTP request/measurement automatically.

### OTel Python SDK Quick Reference

Here's the core pattern:

```python
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.export import PeriodicExportingMetricReader, OTLPMetricExporter
from opentelemetry.sdk._logs import LoggerProvider, LoggingHandler
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor

# Set up tracing
resource = Resource.create({"service.name": "llm-wiki"})
trace_provider = TracerProvider(resource=resource, sampling=sampling_by_default)
trace_provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))
# Note: use http or grpc exporter depending on what Alloy supports

# Set up metrics
metric_reader = PeriodicExportingMetricReader(OTLPMetricExporter())
meter_provider = MeterProvider(resource=resource, metric_readers=[metric_reader])

# Set up logs
logger_provider = LoggerProvider(resource=resource)
handler = LoggingHandler(level=logging.NOTSET, logger_provider=logger_provider)

# FastAPI auto-instrumentation
FastAPIInstrumentor.instrument_app(app)
```

### Structured logging note

OTel's `LoggingHandler` integrates with existing Python `logging` — it does NOT replace the daemon's `JSONFormatter`. Instead, the OTel logging handler adds `trace_id` and `span_id` fields into existing structured log lines automatically. The daemon's JSON formatter stays as-is for file logs; stdout gets OTel-injected trace correlation.

Each JSON object on one line is the pattern consumed by:
- Loki (logcli / Promtail with JSON parser)
- Datadog (Datadog Agent with JSON support)
- CloudWatch/logs (custom dashboard filtering on JSON fields)
- Logstash/Elastic (ingest before mapping)

See Story 1.12 for existing `JSONFormatter` implementation — this story adds OTel trace correlation onto that existing formatter (not a replacement).

### Critical Anti-Patterns to Avoid

- **Never block on OTLP exporter** — OTel SDK uses async `BatchSpanProcessor` and `PeriodicExportingMetricReader` with timeouts internally
- **Never instrument the same request twice by the same otel span** — don't create manual spans for HTTP instrumentation FastAPI. Manual spans only for custom business logic
- **Never use prometheus_client method names** — always call: `from llm_wiki.observability.metrics import query_log_write_failures_counter; query_log_write_failures_counter.add(1)`, not `query_log_write_failures_counter.inc(1)` or `query_log_write_failures_counter.increment(1)`. The OTel Python SDK uses standard method names: `Counter.add(value)`, `Gauge.record(value)`, `Histogram.record(value, ...)`
- **Do not create a second exporter just for metrics** — the metrics endpoint exposes in-memory counters/summaries; the structured logs are for human-readable trails and log aggregation
