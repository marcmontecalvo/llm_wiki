# Story 1.12.5: External Observability Pipeline

**Epic 1: Docker Service**
**Story Number:** 1.12.5 (interstitial — bridges 1.12 and 1.13)
**Status:** backlog

## Story

As a wiki operator running this service in a production-adjacent environment,
I want structured observability (metrics endpoint, structured logging, health signals),
So that I can monitor service health, surface component failures like query-log/database errors to external systems, and gather analytics without SSH-ing into the container.

**Context:** Story 1.12 added `QueryLogStore` with a non-fatal failure path, but there is no external-facing observability surface. If the SQLite log file becomes corrupted or the `state/` directory is read-only, the only signal is a plain-text warning in the startup log — easily missed, not alertable. The service currently has no metrics endpoint, no structured logging format, and no way for a monitoring system (Prometheus, Grafana, Datadog, Loki, or custom) to scrape health or analytics data.

## Acceptance Criteria

1. **Given** the service is running **When** `GET /metrics` is called **Then** it returns text/plain content with Prometheus-format metrics including:
   - `wiki_http_requests_total{method,path,status}` — counter of all HTTP requests
   - `wiki_http_request_duration_seconds{method,path}` — histogram of request latencies
   - `wiki_query_log_init_failed` — gauge: 1 if `QueryLogStore` failed to initialize at startup, 0 if healthy
   - `wiki_query_log_write_failures_total` — counter of failed query log writes (swallowed internally, accumulated here for external visibility)
   - `wiki_index_pages_total` — gauge of total pages in the index

2. **Given** the service is running **When** `GET /v1/health` is called **Then** the response includes a new field `query_log_ok: bool` that is `true` when `QueryLogStore` initialized successfully at startup, and `false` otherwise.

3. **Given** `QueryLogStore` fails to initialize in the FastAPI lifespan **When** the service starts **Then** a `wiki_query_log_init_failed{reason="..."}` gauge is set to 1, the warning is emitted once at startup (not repeated per-request), and `app.state.query_log_error` is set to `True` to signal health checks and monitoring.

4. **Given** any exception occurs in `QueryLogStore.log()` **When** it is caught **Then** the exception message is logged at `ERROR` level AND a counter `wiki_query_log_write_failures_total` is incremented so the failure rate can be trended and alerted on externally.

5. **Given** structured logger middleware is installed on the FastAPI app **When** a request completes successfully **Then** each log line includes `method`, `path`, `status`, and `duration_ms` fields in a structured format (JSON compact, one line) that can be consumed by Loki, Datadog, or similar log aggregation.

6. **Given** `GET /metrics` is called **When** the service has not yet been initialized in a way that exposes index stats **Then** all metrics return 0 rather than erroring — the metrics endpoint must never raise HTTP 500.

## Dev Notes

### Design Decision: Dependency Choice

Two paths for the metrics endpoint:

**Path A — `prometheus-client` + `prometheus-fastapi-instrumentator` (recommended):**
```python
from prometheus_fastapi_instrumentator import Instrumentator
from prometheus_client import Counter, Gauge, Histogram

write_failures_counter = Counter("wiki_query_log_write_failures_total", "Failed query log writes")
log_failed_gauge = Gauge("wiki_query_log_init_failed", "Query log init status")
Instrumentator().instrument(app).expose(app)
```
- Pros: Battle-tested, handles HTTP instrumentation automatically with no per-request code, well-maintained
- Cons: One extra dependency (`prometheus-fastapi-instrumentator` ~15KB), `prometheus_client` transitive (~200KB)

**Path B — Manual, zero-new-dependency:**
```python
@app.get("/metrics")
async def metrics():
    lines = "# TYPE wiki_query_log_init_failed gauge\n"
    lines += f"wiki_query_log_init_failed 1\n"
    return Response(content=lines, media_type="text/plain")
```
- Pros: No new deps
- Cons: Must manually handle every metric type, histogram is painful, no built-in HTTP request instrumentation

**Recommendation:** Path A. The project has accepted `FAISS` (~30MB) as a dependency. A 200KB dependency for metrics is not a trade-off worth making.

### Prometheus Format Basics

```
# HELP wiki_http_requests_total Total HTTP requests
# TYPE wiki_http_requests_total counter wiki_http_requests_total{method="GET",path="/v1/search",status="200"} 142
```

### Structured Logging Note

Use stdlib `logging` with a custom `JSONFormatter` — no new dependency. Each JSON object on one line is the pattern consumed by:
- Loki (logcli / Promtail with JSON parser)
- Datadog (Datadog Agent with JSON support)
- CloudWatch/logs (custom dashboard filtering on JSON fields)
- Logstash/Elastic (ingest before mapping)

```python
import json
import logging

class JSONFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        log_data = {
            "time": self.formatTime(record),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        if hasattr(record, "extra"):
            log_data["extra"] = record.extra
        return json.dumps(log_data)
```

### Critical Anti-Patterns to Avoid

- **Never let `/metrics` raise** — monitoring scrapes it on a fixed interval; a 500 here means you lose observability for the entire outage window
- **Never log per-request in verbose detail** — structured logging adds overhead; keep it to one JSON object per request completion
- **Never block the request on logging** — the log middleware must use `call_next` pattern and never await disk I/O within the handler
- **Do not create a second log file for metrics** — the metrics endpoint exposes in-memory counters/summaries; the structured logs are for human-readable trails and log aggregation
